# v2.0 第二階段：檢測規則引擎實作規格

## 1. 目的

規則引擎將已結構化的 `audit-case` 文件轉換成可重複執行的品質檢查結果。它不取代 42 項人工無障礙檢測，也不從截圖或原始碼自行推論官方合規；它負責檢查案件紀錄是否具備足夠證據、修正資訊、下一步行動、測試環境與一致的摘要。

第二階段的核心成果是：

1. 以 JSON 規則包配置檢查條件，不把所有規則硬編碼在 CLI。
2. 支援 `finding`、`case` 與 `document` 三種規則作用域。
3. 對每個違規項目輸出穩定 `rule_id`、嚴重度、JSONPath 與繁體中文訊息。
4. 同時提供人類可讀文字輸出與 CI 可解析的 JSON 輸出。
5. 允許部分完成案件，但阻止「仍待確認卻宣稱通過」等高風險紀錄。

## 2. 非目標

本階段不實作真實 App 自動操作、TalkBack／VoiceOver 自動判定、影像辨識、Jira 或 GitHub Issue 寫入、官方認證判定、規範內容自動更新，以及跨案件歷史比較。這些功能應在證據模型與規則契約穩定後另行規劃。

## 3. 輸入與輸出契約

### 輸入

規則引擎接受一份符合 `schemas/audit-case.schema.json` 的 JSON 文件，以及一份符合規則包格式的 JSON 文件。Schema 驗證與規則評估是兩個階段；呼叫者應先執行 `validate_audit_case.py`，再執行規則引擎。

```bash
python scripts/validate_audit_case.py examples/audit-case.example.json
python scripts/evaluate_audit_rules.py examples/audit-case.example.json
```

### 文字輸出

沒有違規時：

```text
PASS examples/audit-case.example.json: no rule violations
```

有違規時：

```text
FAIL path/to/case.json: 1 rule violation(s)
  - [high] R-FINDING-EVIDENCE $.findings[0]: 通過或不通過的 finding 必須至少引用一份證據。
```

### JSON 輸出

`--format json` 回傳陣列，適合 CI、報告產生器或後續工單轉換：

```json
[
  {
    "rule_id": "R-FINDING-EVIDENCE",
    "severity": "high",
    "message": "通過或不通過的 finding 必須至少引用一份證據。",
    "path": "$.findings[0]"
  }
]
```

CLI exit code 為 `0` 代表沒有規則違規，`1` 代表 JSON／規則讀取錯誤或至少一項規則違規。

## 4. 規則格式

預設規則位於 [`rules/default-rules.json`](../rules/default-rules.json)。每條規則包含：

| 欄位 | 必要性 | 說明 |
|---|---|---|
| `rule_id` | 必要 | 穩定且唯一的規則識別碼。 |
| `scope` | 必要 | `finding`、`case` 或 `document`。 |
| `when` | 必要 | 規則適用的條件。 |
| `assert` | 必要 | 目標必須滿足的條件。 |
| `severity` | 必要 | `high`、`medium` 或 `low`。 |
| `message` | 必要 | 面向使用者的修正提示。 |

目前支援的條件與斷言如下：

| 類型 | 語法 | 用途 |
|---|---|---|
| 條件 | `status_equals` | 只對指定 finding 狀態套用。 |
| 條件 | `status_in` | 對多個 finding 狀態套用。 |
| 條件 | `field_exists` | 判斷 case 欄位是否存在。 |
| 條件 | `summary_pending_gt` | 判斷文件待確認數量。 |
| 條件 | `summary_overall_not_equals` | 判斷整體結論是否不符合預期。 |
| 斷言 | `field` + `min_items` | 列表至少有指定數量。 |
| 斷言 | `field` + `not_empty` | 字串不可空白。 |

## 5. 預設規則

| 規則 | 作用域 | 嚴重度 | 意義 |
|---|---|---:|---|
| `R-FINDING-EVIDENCE` | finding | high | pass／fail 必須有證據。 |
| `R-FAIL-REMEDIATION` | finding | high | fail 必須有修正建議。 |
| `R-FAIL-NEXT-ACTION` | finding | medium | fail 必須有下一步。 |
| `R-PENDING-NEXT-ACTION` | finding | medium | pending 必須有補證或測試行動。 |
| `R-CORE-ENVIRONMENT` | case | high | 有核心流程時至少要有測試環境。 |
| `R-INCOMPLETE-SUMMARY` | document | medium | pending 大於零時不可宣稱 pass。 |

## 6. 執行模型

規則引擎依文件中的規則順序逐條執行。`finding` 規則會對每個 finding 建立 JSONPath；`case` 與 `document` 規則各執行一次。規則引擎不修改輸入文件，也不自動填入欄位。若需要修正，應由使用者或上層報告工具完成後重新驗證。

規則訊息不應洩漏測試帳號、個資、權杖或原始碼秘密。規則檔本身只描述欄位名稱與一般化訊息，不能放入案件資料。

## 7. 擴充設計

下一階段可加入：

- `all`、`any`、`not` 巢狀條件。
- `equals`、`in`、`matches`、`max_items` 與數值範圍斷言。
- severity policy，例如在 CI 將 high 視為 failure、medium 視為 warning。
- 對 `check_id` 分組的規則，例如 AA-01 至 AA-10 的證據要求。
- 規則套件 metadata、相容 Schema 版本與規則變更摘要。
- SARIF、JUnit XML 與 GitHub Checks annotations 輸出。
- 以 JSON Schema 驗證規則包本身。

擴充規則時必須保持舊規則的 `rule_id` 與輸出欄位相容；若改變判定語意，應提升 `rules_version` 並加入回歸測試。

# v2.0 第三階段：自動化檢測報告生成器實作規格

## 1. 目標

報告生成器將符合 `audit-case` Schema 的案件 JSON、42 項 AA 清單與規則引擎結果轉換成一致的繁體中文 Markdown 報告。它的責任是整理資料、保留證據鏈、顯示平台限制、列出缺失與回歸條件；它不應自行創造測試結果或宣稱官方認證。

## 2. 使用流程

```text
案件 JSON
   │
   ├─ Schema／跨引用驗證器
   │
   ├─ 檢測規則引擎
   │
   └─ 報告生成器
          ├─ 執行摘要與狀態統計
          ├─ 範圍、環境與限制
          ├─ 重大缺失
          ├─ AA-01 至 AA-42 逐項結果
          ├─ 平台測試紀錄
          ├─ 回歸測試計畫
          ├─ 待確認事項
          └─ 規則警告與責任聲明
```

預設情況下，若 Schema 驗證失敗，生成器應停止並回傳 exit code `1`。`--allow-invalid` 只允許產出明確標示為草稿的報告，適合文件編輯或問題診斷，不適合 CI 的正式產物。

## 3. CLI 契約

```bash
python scripts/generate_audit_report.py \
  examples/audit-case.example.json \
  --output reports/audit-case.md
```

| 參數 | 必要性 | 說明 |
|---|---|---|
| `case` | 必要 | audit-case JSON 路徑。 |
| `--output` | 必要 | Markdown 輸出路徑，父目錄不存在時自動建立。 |
| `--rules` | 選用 | 規則包，預設為 `rules/default-rules.json`。 |
| `--checklist` | 選用 | 42 項清單，預設為 `references/taiwan-aa-checklist.md`。 |
| `--allow-invalid` | 選用 | Schema 不通過時仍產生草稿報告。 |

成功時輸出 `WROTE <path>` 並回傳 `0`。輸入檔案遺失、JSON 格式錯誤或正式模式下 Schema 不通過時回傳 `1`。

## 4. 報告章節與資料來源

| 章節 | 主要資料來源 | 生成要求 |
|---|---|---|
| 執行摘要 | `case`、`summary`、`metadata` | 顯示產品、版本、案件編號、結論、狀態數量與規則狀態。 |
| 範圍與限制 | `case.platforms`、`flows`、`test_environments`、`evidence` | 明示平台、裝置、OS、輔助工具與材料限制。 |
| 重大缺失 | `findings` 中 `status=fail` | 依嚴重度列出 finding、影響使用者、責任角色與修正方向。 |
| 逐項檢核 | 42 項清單與 `findings` | 永遠輸出 AA-01 至 AA-42；未記錄項目標示待確認，不可省略。 |
| 平台測試 | `test_environments` 與 evidence | 逐環境列出裝置、OS、輔助工具、設定、流程與證據。 |
| 回歸測試 | `finding.regression` | 顯示修正內容、步驟、預期、實際結果與狀態。 |
| 待確認 | 未記錄或 pending findings | 列出需要補實機、讀屏或其他證據的項目。 |
| 聲明 | 固定文字 | 保留非官方認證與證據範圍聲明。 |

## 5. 狀態與部分完成案件

生成器應支援完整案件與部分完成案件。若 findings 只記錄一部分，仍需產出全部 42 個檢核列；未出現的 `check_id` 使用待確認狀態。`summary.pending` 應沿用已驗證案件的統計，不由報告生成器偷偷改寫輸入。

若規則引擎有違規，報告最後加上「規則引擎警告」段落，包含 `rule_id`、嚴重度、JSONPath 與訊息。報告生成器可以在 `--allow-invalid` 草稿模式繼續產出，但應保持警告可見。

## 6. 安全與品質要求

生成器必須以 Markdown table cell escaping 處理 `|` 與換行，避免證據描述破壞表格。不得重新輸出密碼、權杖、付款資料或未遮罩個資。證據來源只顯示使用者提供的來源指標；若案件含敏感資料，應由 Schema 或上游流程先拒絕。

生成器不能把 `observed`、`inferred` 或截圖證據升級為 `reproducible`。平台測試表中的「待依實機結果填寫」是有意的保護機制，除非案件明確提供對應人工測試結果。

## 7. 測試策略

至少包含下列自動化測試：

1. 有效範例產生報告並包含 42 個 AA table rows。
2. 報告包含摘要、重大缺失、平台紀錄與待確認事項。
3. 規則違規會出現在報告的警告段落。
4. Schema 無效時預設停止且不產生正式報告。
5. `--allow-invalid` 可以產生草稿報告。
6. 表格內容中的 `|` 不會破壞 Markdown 結構。
7. 報告產生不會修改輸入案件 JSON。

# 第二版功能與擴充藍圖

## 1. 第二版目標

第二版應將本 Skill 從「規範導向的人工檢核顧問」提升為「可管理證據、可協作分工、可產生工程工單與支援半自動檢測的無障礙 QA 工作台」。核心原則是不以自動化工具取代人工判斷，而是讓人工檢測更有一致性、可追蹤性與可重複驗證性。

第一版已經具備 42 項 AA 架構、平台人工測試流程與報告模板；第二版的工作重點應放在**證據結構化、跨平台差異、工程落地與版本治理**，而不是單純增加更多說明文字。

## 3. v2.0 核心功能

### 3.1 結構化檢測案件

加入案件初始化格式，讓 Skill 能以固定欄位建立檢測專案：產品名稱、產品類型、版本、平台、裝置、OS、輔助工具、測試帳號、核心流程、檢測日期、執行人、證據清單與排除範圍。輸入不足時，Skill 應先列出缺少的必要欄位，不要直接產生看似完整的合規結論。

建議支援 YAML 或 JSON 匯入，以便把同一案件交給不同人員或不同 AI Agent 續作。每一項檢核都應有穩定 ID、狀態、證據引用、問題描述、嚴重度、負責角色、修正版本、回歸結果與最後更新時間。

### 3.2 證據管理與可追溯引用

第二版應提供證據索引規則，例如 `E-001` 代表登入畫面截圖、`E-002` 代表 TalkBack 錄音、`E-003` 代表原始碼片段。逐項檢核只引用證據 ID，不在不同文件重複貼上無法追蹤的描述。對於截圖、錄影與原始碼，應記錄檔名、取得日期、裝置、OS、版本與雜湊或版本識別資訊。

這項功能可以明確區分「已觀察」、「由原始碼推定」與「尚未驗證」，降低錯把視覺初檢當作完整讀屏測試的風險。

### 3.3 截圖與錄影輔助初檢

當使用者提供截圖時，第二版可以協助檢查文字截斷、資訊是否只依賴顏色、控制項名稱是否可能缺失、觸控目標是否疑似過小、錯誤訊息是否顯眼但不具語意，以及放大文字後的版面風險。當提供錄影時，可擷取流程節點、畫面轉換、彈窗、載入與錯誤狀態，建立待人工確認的檢核項目。

此模組必須把結果標為「視覺初判」或「操作可見證據」，不能僅從畫面推論 TalkBack 或 VoiceOver 已經正確讀取。

### 3.4 工程工單產生器

每個不通過項目應能轉換為 GitHub Issue、Jira、CSV 或 Markdown 工單。工單至少包含問題標題、檢核編號、重現步驟、實際結果、預期結果、受影響使用者、證據連結、建議修正方向、優先級、負責角色與回歸測試條件。

建議提供三種輸出視角：產品與設計摘要、工程實作說明、QA 驗證案例。相同缺失若涉及共用元件，應能合併為一張主工單，再列出受影響畫面，避免團隊收到大量重複任務。

## 4. v2.1 平台與框架擴充

### 4.1 Android 原生

增加 Android Views、XML、AccessibilityNodeInfo、contentDescription、stateDescription、重要性設定、焦點管理、LiveRegion、EditText 錯誤訊息與自訂 View 的修正模式。每個建議都應附上「適用條件、可能副作用與 TalkBack 回歸步驟」，避免工程師直接複製不適用的屬性。

### 4.2 iOS 原生

增加 UIKit 與 SwiftUI 的 accessibilityLabel、accessibilityValue、accessibilityHint、accessibilityTraits、accessibilityIdentifier、焦點管理、通知與自訂元件修正模式。應特別處理動態內容、表單驗證、可調整控制項、頁面轉場與 VoiceOver 焦點恢復。

### 4.3 跨平台框架

加入 React Native、Flutter、Jetpack Compose 與 SwiftUI 的常見元件對照表，說明同一個無障礙需求在不同框架中的實作位置。這些範例應以最小可用片段呈現，並附上平台實機驗證要求，不要宣稱單靠靜態程式碼即可跨平台通過。

## 5. v2.2 開發流程與自動化整合

### 5.1 CI／PR 檢查

提供可選擇的命令列檢查器，在 Pull Request 中檢查常見風險，例如圖片缺少替代文字、互動元件缺少名稱、表單控制項缺少標籤、重複 ID、可見文字與可讀名稱不一致，以及測試案例沒有回歸證據。自動檢查只能作為提示與門檻，不應取代 TalkBack、VoiceOver 與人工流程測試。

### 5.2 GitHub 與專案管理整合

支援從 GitHub Issue 讀取修正狀態，再回寫檢測報告中的狀態。對每個檢核項目建立穩定的 issue key 或外部追蹤 ID，讓產品版本、修正 PR、測試證據與報告互相連結。若日後加入 Jira 或其他服務，應採用明確的權限範圍與最小化資料傳送原則。

### 5.3 版本差異與回歸比較

第二版應能比較兩次檢測：哪些項目由不通過變為通過、哪些項目退步、哪些項目因流程改變而不適用，以及哪些問題仍缺少證據。輸出應包含「改善項目、退化項目、新增問題、未變更問題與待確認項目」五種分類。

## 6. v2.3 規範治理與品質保證

### 6.1 規範版本標記

每份報告應記錄採用的規範名稱、版本、來源網址、文件查閱日期與適用範圍。當官方文件更新時，Skill 應提示使用者重新確認檢核項目是否仍然適用，而不是默默沿用舊版內容。

### 6.2 可配置檢核集合

在保留完整 AA 集合的前提下，允許建立「核心流程快速檢查」、「完整 AA」、「上市前驗收」、「修正回歸」與「行動 Web」等檢核視圖。每個視圖都必須清楚標示省略項目，避免使用者誤以為快速檢查等同完整檢測。

### 6.3 內部品質檢查

加入報告自動檢查規則：所有不通過項目必須有證據或重現說明；所有待確認項目必須有下一步；所有不適用項目必須有理由；所有重大缺失必須有回歸條件；平台結論必須帶有裝置、OS、版本與輔助工具。這些規則能讓報告在交付前先發現結構性缺漏。

```yaml
case:
  product: ""
  version: ""
  platforms: [android, ios]
  devices: []
  assistive_technologies: [talkback, voiceover]
  flows: []
  scope: ""
  standard:
    name: "台灣行動版無障礙檢核架構"
    revision: ""
    source_url: ""

evidence:
  - id: E-001
    type: screenshot
    path: ""
    platform: android
    os_version: ""
    captured_at: ""

findings:
  - id: AA-01
    status: pending
    evidence_ids: [E-001]
    severity: high
    observation: ""
    remediation: ""
    owner_role: engineering
    regression:
      steps: []
      expected: ""
      result: pending
```

資料模型的重點不是要求使用者一定要手寫 YAML，而是讓報告、工單、回歸測試與版本比較共享同一組穩定欄位。

## 8. 不建議在第二版直接加入的功能

不建議在 v2 初期承諾「自動判定官方認證結果」、「只靠截圖完成完整無障礙驗收」、「自動操作需要真實帳號的 App」、「直接替使用者提交政府申請」，或「以單一分數代表所有障礙使用者的體驗」。這些功能容易造成過度信任、資料風險與責任界線不清。

若要支援自動化操作，應先建立測試帳號、資料遮罩、操作範圍、人工覆核與停止條件。若要支援規範同步，也應保留來源版本、變更 diff 與人工審查流程。

## 9. 第二版完成定義

第二版可以在下列條件達成時視為可發佈：

1. 使用者可以用固定格式建立一個檢測案件，並在沒有完整資料時得到明確的補件清單。
2. 每個檢核結果都能追溯到證據、觀察、修正建議與回歸測試。
3. 報告可以轉出至少一種工程工單格式，且不遺失檢核編號與證據引用。
4. 截圖或錄影分析會清楚標記推論限制，不會把視覺結果冒充實機讀屏結果。
5. Android 與 iOS 平台建議能區分原生與跨平台實作，並提供對應回歸測試。
6. 兩個版本的檢測結果可以比較，並能辨識改善、退化、新增與待確認項目。
7. 變更後的 Skill 通過結構驗證，且文件、模板、範例與版本紀錄同步更新。

## 10. 建議開發順序

最實際的開發順序是先完成案件資料模型與證據索引，再完成工單與回歸輸出，接著加入截圖／錄影初檢，最後才投入 CI、平台框架範例與儀表板。這樣可以先建立穩定的核心資料流，避免未來每增加一種輸入或輸出格式就必須重寫整份報告。
